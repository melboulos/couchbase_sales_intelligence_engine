Sales Intelligence Platform — Architecture

What each stage does, what file it lives in, and when it gets called — traced from real source code, in the order the pipeline actually runs.

Worth emphasizing when presenting this: there are two genuinely different web searches in this system, serving two different purposes — one cached and free (used for classification), one live and per-account (used to ground the AI's actual write-up). See Stage 5.

0 Universal grounding pre-pass

Give every account a fair shot at real signal, before scoring begins
serper_enrichment_pass.py
Runs a real web search for every account in the list, not just ones whose name already hints at what they do. Results are saved to a single shared cache file, keyed by account name — reused across any account list this pipeline ever processes, not tied to one dataset.
Run this once, on its own, before main.py. It's checkpointed and resumable — running it again against the same list costs nothing for accounts already cached; only new accounts get searched.

1 Load and grounding merge

main.py starts here
pipeline/loader.py→load_accounts()
Loads the raw account list (auto-detects a common Salesforce export quirk where a .xls file is actually an HTML table internally). Immediately after loading, it reads Stage 0's cache file — once, here, before anything else runs — and attaches each account's saved search result as a new column. If Stage 0 was never run, this step degrades gracefully to an empty column.

2 Classification — name first, search as a fallback

Every account gets two chances to be classified correctly
industry_classifier.py + company_intelligence.py
First attempt: match the account's own name against a curated list of known companies and industry keyword patterns. Fast and reliable, but blind to any company whose name doesn't reveal what it does.
Second attempt, only if the first found nothing: fall back to Stage 0's cached search result and try the same keyword matching against that text instead. A real name-match is never overridden by this fallback — the fallback only ever fills in where the first attempt drew a blank.
Known limitation: a company that sells to an industry (say, software sold to utility companies) can sometimes get classified as if it were that industry, since the same keywords show up either way. This is judged case-by-case rather than solved with one general rule, since a broad fix risks blocking genuinely correct matches.
Non-Profit / Charity classification
Accounts that match nonprofit/charity language get their own explicit category, rather than falling into a generic "unclassified" bucket — so it's clear at a glance that the account was reviewed and genuinely is a nonprofit, not simply unprocessed.
Business model
Alongside industry, each matched pattern also carries a business model label (FinTech, Healthcare Technology, Retail, Utility, and so on), which in turn drives category-specific AI-opportunity messaging later in the account's writeup.
Known limitation: business model currently only gets set when the pattern-matching step itself finds a match. If an account's industry comes from some other signal instead, business model can be left blank even though industry is populated — industry has a broader safety net than business model does today.

3 Ownership / rebrand signal detection

A free, deterministic check — no AI, no new search
modules/ownership_signal_detector.py
Scans the same cached search text from Stage 0 for plain-language signals of a recent acquisition or rebrand — phrases like "is now," "acquired by," "now part of." This is pure text matching against data already retrieved, so it costs nothing extra to run.
The idea: a rep calling a company by an outdated name, or pitching a team that no longer holds purchasing authority after an acquisition, is an avoidable mistake. Roughly one in twenty accounts shows a real signal here.

4 Scoring, explanation, and the gate

Every account gets a number; only the strongest move forward
scoring_engine.py → opportunity_explainer.py → deterministic_gate.py
The Couchbase Opportunity Index combines five weighted signals: workload fit, database opportunity, real-time requirement, technical environment, and company context. A separate gate then decides which accounts are worth the expensive step ahead — an account needs both a real workload signal and a score above the threshold to qualify.
Everything below this line only runs for accounts that clear the gate. Everything else is skipped, at zero further cost.

5 AI-generated sales intelligence

The two searches, side by side
Stage 1's cache and this stage's search are two separate things, serving two separate purposes — worth being precise about which is which when explaining this system.

Stage 1 — cached search

When: read once, up front
Purpose: classify industry / business model
Cost: free — already retrieved, reused
Visibility: never shown to the AI directly

Stage 5 — live search

When: fresh, per qualifying account
Purpose: ground this specific AI write-up
Cost: real, ongoing, every run
Visibility: fed directly into the prompt
What happens, per account, in order
sales_intelligence_pipeline.py :: validate_account()
  1. The gate is checked again at the individual-account level (a safe, cheap re-confirmation).
  2. The account's location is read, used to disambiguate common company names in the search that follows.
  3. A live search runs for this specific account — includes automatic retry with backoff if a request is rate-limited or times out.
  4. A prompt is built combining the account's data and the fresh search result. The prompt explicitly bans naming Couchbase or "database" in one specific field, and asks the model for an independent opportunity score computed without seeing the deterministic score above — so the two can later be compared.
  5. The request goes to Bedrock (meta.llama3-70b-instruct-v1:0).
  6. The response passes through roughly fifteen validation checks before being trusted: does the model genuinely recognize this company (not just guess from the industry label), is the score backed by real evidence rather than generic reasoning, does the stated scale match reality, is the company still operating, is any of this hallucinated.
Why this stage checks itself so heavily: a model can sound confident while being wrong, especially about a company it doesn't actually know. These checks exist to catch that before it reaches a rep, not to slow things down for its own sake.

6 Merge and export

Bringing it back together
Only accounts that passed validation get merged back into the full dataset, matched by account name. intelligence_export_pipeline.py then writes both a scored Excel file and a JSON file for the Streamlit dashboard.
At the end of every run, a summary line reports what fraction of validated accounts actually received a live search result — a quick, built-in health check on whether grounding is working as expected.

What a rep sees on the call brief

🔍 Web-Verified

This account's story is grounded in a real, live Stage 5 search — not just the model's own memory.

⚠ Not Company-Verified

The model didn't genuinely recognize this specific company. The narrative is built on its assigned category — worth confirming before outreach.

🏢 Possible Ownership Change

Stage 3's free check found language suggesting a recent acquisition or rebrand — worth confirming current ownership before the call.

Independent score vs. deterministic score

Two separate scoring methods, computed without seeing each other. When they land close together, that agreement is a genuine signal, not a coincidence.
